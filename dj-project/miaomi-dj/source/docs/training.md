## 用按钮提交反馈

双击根目录 `Start-Feedback.cmd`，或运行：

```powershell
.venv\Scripts\python.exe -m dj_agent listen outputs\weeknd-first-listen-20260924\listening --open
```

页面可以选择选曲搭配、每版切入点/混音衔接/人声交接，以及整体 A/B 偏好。只填有把握的项；未评价不推断为好或坏。选择后需点击“保存反馈”。本地服务仅监听 127.0.0.1，使用随机请求令牌，不上传数据。

新评分追加到会话内的 `structured-feedback.jsonl`，保存绑定音频和比较清单的哈希。刷新可恢复；重复请求不产生重复记录；旧页面覆盖新评分会被拒绝。会话文件锁覆盖网页、CLI 保存及读取，避免多进程同时修改造成历史分叉。更新保留历史，训练只取该比较的最新整体选择；后来的 CLI/chat 选择也进入同一修订链。

现有四条选择载入页面作为历史反馈，没有为未评价的细项编造标签。当前音频偏好模型只消费总体 A/B/tie 选择，新维度先存档，尚未作为训练特征。人声修订标签仍单独存档，不混入原 baseline/enhanced 排序器。

## 这一轮训练什么

第一版是一个 CPU 上的成对逻辑回归排序器，学习“同一转场的两段实际录音，听者更喜欢哪一段”。输入为音频片段的 7 项测量：RMS 电平、峰均比、20–180 Hz 能量占比、短时电平变化范围、相邻帧电平变化、立体声侧向能量和静音比例。它不读取歌手名、文件名、A/B 字母或 baseline/enhanced 版本名作为学习特征。

它只能学习这些有限特征与听者选择的关系，尚不能理解歌词、识别真正的人声冲突、判断现场气氛，也不负责选下一首歌。候选仍由已验证的规划和渲染程序生成。音频特征在播放前提取，模型不占用实时音频线程。

本机已有 NumPy / SciPy，可直接拟合这个小模型，无需新增依赖、CUDA 或云服务器。没有启动 GLM、Open-Jev 或 KEV 微调，也没有将现有 CPU PyTorch 环境改为 GPU 环境。是否值得训练更大模型，必须由未来真实歌曲上的独立结果决定。

## 数据怎么来

1. 把完整的实际歌曲放入 `D:\DJ_agent\weeknd`。首先做少量听评，确认两种处理有可听差别。
2. 使用 `compare` 渲染同一区间的两个候选。新会话采用 schema 2，A/B 随机排列，避免总选 B 的位置偏差。每段音频保存 SHA-256 和特征版本。
3. 听完选择 `A`、`B`、`tie`（接近）或 `neither`（都不好）。音频分析自动完成，不需要手工标每一拍或写 DJ 操作轨迹。
4. 为歌曲建立统一身份表，确认同一歌曲的转码、裁剪、增益、不同文件和版本归入同一组。训练会检查这个表已审阅。
5. 运行训练入口；数据不足会输出具体原因，不会产生伪模型。

```powershell
.venv\Scripts\python.exe -m dj_agent compare 'D:\DJ_agent\weeknd\song-a.flac' 'D:\DJ_agent\weeknd\song-b.flac' --minutes 4 --output outputs\comparison-001 --open
# 仅在您确实听过并选择后记录下面的标签；B 只是命令示例。
.venv\Scripts\python.exe -m dj_agent feedback outputs\comparison-001 transition-01 B
.venv\Scripts\python.exe -m dj_agent train --check-only
.venv\Scripts\python.exe -m dj_agent train
```

`train` 默认读取 `outputs` 下的反馈和 `data/song-identities.json`，将每次结果放入新的 `outputs/training-*`。可以通过 `--sessions`、`--identity-map`、`--output` 指定其他位置。已有输出目录不覆盖。

身份表示例（键替换为实际 `comparison.json` 中的文件 ID，值由人工确认；不能原样用于训练）：

```json
{
  "schema_version": 1,
  "reviewed": true,
  "songs": {
    "file-sha256-for-song-a": "the-weeknd-song-a",
    "another-encoding-of-song-a": "the-weeknd-song-a",
    "file-sha256-for-song-b": "the-weeknd-song-b"
  }
}
```

源文件 SHA-256 本身不是歌曲身份识别；换编码或改标签就会变化。`reviewed: true` 是本地人工确认，不是程序已自动识别所有重复歌曲的证明。`source_kind: user-local-audio` 也只是来源声明，不能自动证明艺人、版权或录音真实性。

## 标签处理与隔离规则

- 反馈追加保存，并绑定提交时的 `comparison.json` 哈希。训练重新核对清单、音频哈希、特征、歌曲 ID。文件变化就拒绝，不悄悄重新解释旧选择。
- 旧 schema 1 会话仍可保存反馈，但不能自动用于新训练，需要对 schema 2 的实际候选重新听评。历史文件保持不变。
- 同一音频比较的重复点击或复制会话只计一对，A/B 反转也会统一方向。互相冲突的选择整对排除，报告计数，保留原始反馈供复查。当前面向单个听者，没有多听者投票建模。
- `tie` 作为目标概率 0.5；`neither` 记录为两者均不接受，暂不用于相对排序。它不是“两个都一样好”。
- 合成工程音频、不明来源、自动生成标签、损坏记录和缺身份映射的记录不进入真实偏好实验。自动技术检查不会调用人类反馈入口。
- 先按统一歌曲 ID 的连通分量划分，再计算训练特征缩放和拟合权重。共享歌曲的比较，包括链式共享，必须在同一侧。全部相连时拒绝训练，不改用随机逐行拆分。

## 训练与评测门槛

固定 seed 17，目标测试比例 20%，以完整歌曲组为单位分配。至少需要 **训练侧 20 对明确偏好、测试侧 10 对明确偏好；训练侧 3 个独立歌曲组、测试侧 2 个**。`tie` 不计入明确偏好数量。实际划分可能不同于 80/20，因此总数超过 30 对不一定够；少量歌曲反复复制或反复打分不能达到门槛。

这些是防止无意义小样本结果的工程下限，**不是统计显著性或“50 对就能学会 DJ”的承诺**。先听 5–10 对检查标签是否有意义，再逐步收集独立曲组；不能为了凑数生成假偏好。当前仅比较普通淡化与低频交接两类候选，听感学习范围很窄。

模型采用无截距的成对逻辑回归、L2=0.1、L-BFGS-B。缩放只使用训练侧差值的均方根，未变化的特征维度屏蔽。A/B 互换时预测互补，同一候选对自身为 0.5。测试集不用于调参。报告保存划分成员、数据摘要哈希、训练与测试交叉熵、明确偏好准确率，以及“恒定选择”和“总选增强版”基线。恒定选择基线使用按音频哈希统一后的候选方向，不是屏幕上的 A/B 位置。

训练输出：

- `report.json`：`needs_data`、`ready_for_training` 或 `trained_experimental`，样本审计、排除原因、设备和耗时。
- 仅成功训练后输出 `model.json` 和 `dataset.json`，包含可重现的数据、缩放与权重。权重标记 `experimental_not_enabled`。
- `--check-only` 不拟合、不导出权重；正常完成审计退出 0。实际 `train` 数据不足退出 2。

模型不会自动接入播放或替换规则，测试结果也不自动批准部署。还需要真实音乐盲听、更多独立歌曲以及重复实验，才能判断是否优于基线。保存的测试集反复用来改模型会形成间接过拟合，应另外保留最终验收集。

## 公开数据的作用

2026-09-24 核对官方项目页面：

- [DJ Mix Dataset / transitions](https://huggingface.co/datasets/djmix/transitions)：64,748 条转场记录，包含重叠长度、匹配率和 cue 时间等；没有本项目听者对两个候选的偏好字段。可研究转场统计，不能直接假装成人类好坏标签。
- [M-DJCUE](https://github.com/MZehren/M-DJCUE)：专家 cue 点标注可支持切入点研究；未标注点不能全部当成负例。
- [Harmonix Set](https://github.com/urinieto/harmonixset)：节拍、重拍与段落标注可用于分析模块研究；不等同于带音频和本地审美评分的完整训练包。

本轮未下载这些数据集、未训练公开数据模型。也未把互联网上的 DJ 演出默认作为授权音源或偏好金标准。

## 当前验证边界

自动化测试确实运行梯度优化，并验证从片段、反馈、独立划分到训练导出及重载预测的流程。它使用临时目录中的合成音调与明确的人工构造规则，**只是程序正确性测试，不是个人偏好训练成绩**。真实曲库和人工反馈为空时，正常结果就是 `needs_data` 且没有权重文件。
